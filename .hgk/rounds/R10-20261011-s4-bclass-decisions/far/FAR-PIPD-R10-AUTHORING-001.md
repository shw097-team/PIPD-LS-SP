## 1. The decision actually being made

The three rows are `EVIDENCE_GAP` because the object each requires does not exist. The tempting read is
"then create the objects and the rows go away". That read is wrong, and this study exists to say why.

There are two different questions hiding in one:

- **Does the artefact need to exist?** — an engineering question, answerable here.
- **Should this project claim it has it?** — a scope question, and answering it by manufacturing the
  artefact is the failure mode: an object brought into existence to move a coverage counter evidences
  nothing about the system it describes. `EXISTS != TRUE`, the sibling of the project's existing
  `EVIDENCED != PASS`.

So each row is adjudicated on whether the artefact can be produced as a **truthful RESTATEMENT of
material already present** — every field traceable to a named existing file — or would require
**invention**.

## 4. Why the MCP record is flagged provisional rather than presented as an object

The row asks for "a materialization object", but **no PIPD schema for such an object exists**, and
defining a schema is a design act with its own authority. Presenting a newly-invented schema as
canonical would be a second, subtler fabrication — a false claim of authority rather than of content.
The record is therefore emitted as an **evidence record requiring ratification**, and says so in its own
body. If the owner reads "materialization object" as *an object proving MCP IS materialized*, the row
degrades to `NEEDS-OWNER-DESIGN-DECISION` and cannot be satisfied honestly at all.

## 5. What this does NOT claim

- **That any row is now `PASS`.** `EVIDENCED != PASS`. Two rows acquired truthful evidence this round;
  the crosswalk was **not** edited, and re-classifying its rows is not this round's act.
- That the deferred 19 rows, the external dependencies, or the absent external acceptance changed.
- That the 22 declared technology adapters are usable. They are declared and **not installed**; the
  registry says so.

## 6. Refusals, stated plainly

1. **Refused**: authoring a `PIPD-LIFECYCLE-SPEC@1.1.0` copy to close `PIPD-SP-SPEC-002`. It is
   external, and copying it would break the row's own prohibition.
2. **Refused**: a positive MCP materialization object. The material contradicts it.
3. **Refused**: dressing the MCP record in an invented canonical schema.
4. **Refused**: editing the crosswalk or any validator to convert these rows. If they are to be
   reclassified, that is a recorded owner decision, not a side effect of an authoring pass.
